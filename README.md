# devkeep-workflows

Public host for [Devkeep](https://github.com/BubbaF377/devkeep)'s reusable GitHub Actions workflows. Copied from [devlore-workflows](https://github.com/BubbaF377/devlore-workflows) on 2026-08-24 (full history preserved) when Devkeep got its own caller-workflow-facing repo, distinct from standalone Devlore's.

Devkeep itself is private, and GitHub only allows a public repository's workflow to call a reusable workflow (`uses: owner/repo/path@ref`) that's *also* hosted in a public repository — a public caller can never reach a private one, regardless of any repository access settings. Splitting these thin orchestration files out here lets Devkeep work with both public and private linked project repos, without making the actual application source public.

Every file here is pure orchestration — checkout, install, run one script — with zero business logic, prompts, or proprietary code. Six workflows remain, on two execution models:

- **`draft-log-entry.yml`, `consolidate-release.yml`, `crypting-candidates-scan.yml`, `sync-onboarding.yml`, `draft-release-notes.yml`** — install `@starterculture/devkeep-actions` at an exact pinned version and run one bundled entrypoint. **Changed 2026-09-02, and this is the change that makes Devkeep usable by anyone who isn't its author.** They previously checked out the private `BubbaF377/devkeep` at runtime, which needed a `devkeep-github-token` that could read Devkeep's own source — something only the account that owns it ever had. A linked project's token now needs nothing beyond its own repo and the vault, which it still writes the results into.
- **`devseer-review.yml`** — checks out Devkeep's private source and builds it. Deliberate, and not on its way anywhere: Devseer's review methodology must never be published, so this is the one job that cannot move to a public package. The consequence is accepted rather than overlooked — Devseer's CI review works only for the account that owns the source.

**Six other workflows were removed on 2026-09-03**: `analyze-codebase.yml`, `capture-baseline-draft.yml`, `capture-baseline-seed.yml`, `sync-test-plan.yml`, `sync-user-manual.yml`, and `sync-visualizer.yml`. Each had been retired on 2026-09-02, when its generation moved to local, click-initiated execution inside Devkeep — which is what keeps prompts like `buildTestPlanPrompt` and `buildUserManualPrompt` off a public registry entirely. They were kept here for repos linked before that change, and five of them still installed the deprecated `@starterculture/devlore`.

What kept them alive was a real bug rather than a real dependency: Devkeep's `linkRepo` wrote the current caller workflows but never removed retired ones, so four repos still carried callers for jobs nobody generates — after all four had been re-linked. Linking now converges on the current set, the orphaned callers are gone, and nothing references these six. Recovered from git history if ever needed.

`devseer-review.yml` is the one file here whose source of truth lives elsewhere: it is authored in Devkeep at `modules/devseer/workflows/devseer-review.yml`, beside the code it runs, and copied here because only `.github/workflows/` executes. Edit it there and copy across; a Jest test in that module checks it against the CLI's required environment.

The five bundle-installing workflows pin an **exact** version, never a range or `latest`, and are kept on the **same** version as each other. With a floating pin, one publish changes behaviour under every linked project simultaneously, with no version boundary to debug against and no way to hold a repo back. Upgrading is therefore a deliberate edit here, which is the intended cost — but it has to be *every* file, not just the one whose code changed. Every publish rebuilds all five bundles from the same source, so a workflow left on an older pin runs genuinely older logic for everything it touches, not just for its own entrypoint. Found the hard way on 2026-09-02: the pins had drifted across three versions (0.1.0, 0.2.0, 0.3.0) because each port only repinned the file it was about, and a fix shipped for `consolidate-release` would have been inert, since that file was still pinned two minor versions back. Devkeep's own `check-bundle-drift.yml` warns when the published bundle falls behind its source.

Not meant to be used standalone — these are called by Devkeep's own "Link a project" flow when it links a project repo.
